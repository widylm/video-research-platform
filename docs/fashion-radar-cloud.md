# Облачный Fashion Radar: подготовленный перенос сборщика

## Что было в присланном архиве

`collector.rar` содержит основной сборщик и его тесты. `Start-Collector.cmd`
запускает `collector/launch.ps1`, затем Node.js и локальный HTTP-сервис. Основные
модули работают без npm-зависимостей. Поэтому отсутствие package.json не мешало
разобрать алгоритм. Старый интерфейс ссылается на файлы за пределами collector,
но для извлечения роликов они не нужны.

Windows-версия запускает обычный Chrome, сохраняет `browser-profile` на диске,
ждёт ручного входа при необходимости и читает JSON, который загружает страница,
а также данные внутри HTML. Это объясняет, почему локальная версия могла
получать данные, которых нет у нового браузера в облаке.

В `workers/cloud-browser/fashion-radar/` сохранены без изменения логики три чистых
модуля из пользовательского архива: `extract.mjs`, `instagram.mjs`,
`page-state.mjs`. Адаптер `metadata.mjs` использует их нормализацию и добавляет
счётчик комментариев, автора и полное описание в пределах контракта «Кадра».
Профили Chrome, cookies, результаты поиска и данные входа не копируются.

## Изменения сайта

- «Каталог видео» ищет только реальные сохранённые записи, `is_mock = false`.
  Исторические демонстрационные строки в базе не удаляются.
- «Сбор роликов» запускает отдельную серверную задачу TikTok или Instagram:
  хэштег/слова, все даты/сутки/неделя/месяц, до 50 результатов.
- Фиктивный массовый поиск и нейтральная страница больше не подставляются в
  рабочий раздел. Без подключения исполнителя показано состояние настройки.
- Поиск продолжает выполняться, если закрыть вкладку. Последний результат
  участника хранится в Durable Object и восстанавливается при возвращении.
- Отображаются исходная ссылка, описание, дата и доступные счётчики. Неизвестные
  значения остаются NULL, нули сохраняются. Фото из Instagram /p/ не становятся
  видео без подтверждающих данных.
- «Сохранить в каталог команды» использует действующий save_public_video с
  правами текущего пользователя. Новая миграция и service_role не требуются.
  Повторное сохранение не заменяет ручные правки существующей карточки.

Исходные комментарии и fetchedAt видны в последнем результате серверной задачи.
Существующий каталог Supabase сохраняет дату с точностью до дня, описание до
2200 символов, просмотры и лайки. У него пока нет полей комментариев и истории
измерений. Новый запуск заменяет последний результат участника; нужные ролики
следует сохранить в каталог. Это первая версия сбора, без мониторинга роста.

## Чем облачная версия отличается от локальной

Она использует Cloudflare Browser Run вместо запуска chrome.exe. Странице
разрешены её скрипты и обычные запросы данных, включая POST GraphQL Instagram;
одного чтения HTML сразу после навигации недостаточно. Сбор ждёт появления
контента, прокручивает выдачу и проверяет ограниченное число исходных страниц.

Для бесплатного пилота объём намеренно меньше локального: до восьми шагов
прокрутки, до пяти страниц подробностей, обычный таймаут 45 секунд. Максимум 50
означает верхнюю границу, а не гарантированное число подходящих видео.

Вход из Chrome пользователя не переносится. При видимой проверке на человека
сбор приостанавливается и владелец задания получает кнопку открытия того же
окна через Cloudflare Live View. После ручного Done сбор повторно проверяет
страницу и продолжает исходный запрос. На всё ожидание даётся до двух минут,
на запуск с ручным этапом — до 170 секунд. Повторная проверка не запускает
бесконечный цикл: если она остаётся видна, задача завершается явной ошибкой.
Скрытые окна, прозрачные/вынесенные за экран элементы и небольшие значки
CAPTCHA не считаются видимой проверкой. Разрешены изображения с известных
доменов, чтобы пользователь видел саму проверку; загрузка видео блокируется.

Автоматический вход, сохранение профиля между заданиями, перенос cookies и
автоматическое прохождение проверок не реализованы. Если соцсеть требует входа
или отказывает самому облачному браузеру, наличие Live View не гарантирует
работоспособность. Нужен отдельный живой тест. Поддержка
ключевых слов Instagram тоже зависит от доступности его страницы поиска;
хэштеги и слова отправляются на разные страницы.

Пустому первому отображению даётся до восьми ожиданий по две секунды в пределах
общего таймаута. Отсутствие первых ссылок не считается концом списка. Объект
статуса локального TikTok корректно преобразуется в требование входа, ручной
проверки или ошибку загрузки. При ошибке экран раскрывает статус HTTP,
заголовок страницы, время ожидания, число ссылок/ответов/записей, сетевые ошибки
и до 12 доменов ресурсов, остановленных самим сборщиком. Диагностика не содержит
URL запросов, их параметров, заголовков, cookies и текста страницы в текстовых
полях. Она помогает
различить сбои загрузки; сама по себе не доказывает блокировку соцсетью.

Живая диагностика выявила три служебных домена TikTok, которые отсутствовали
в начальном списке ресурсов: mssdk16-normal-useastred.tiktokw.eu,
verification16-normal-useastred.tiktokw.eu и
starling16-normal-useastred.tiktokv.eu. Разрешены ровно эти адреса для обычных
ресурсов страницы TikTok; навигация на другой сайт и загрузка видео остаются
закрыты. Проверки на странице по-прежнему останавливают сбор. Для последних
четырёх наблюдаемых ответов выдачи диагностика также сохраняет HTTP-статус,
числовой statusCode/status_code (если он есть), формат и количество извлечённых
роликов. Успешный HTTP 200 без данных не превращается в успешный пустой поиск.

### Доступ к ручному окну и снимкам

Используются штатные команды Cloudflare.getLiveView/Cloudflare.handoff и событие
Cloudflare.handoffComplete через существующий Browser binding. Дополнительный
API token не нужен. Ссылка принимается только на HTTPS live.browser.run/ui/view
или /ui/inspector с WebSocket этого же провайдера. Её получают только активные
редакторы и только для собственного задания через защищённый API. Временная
ссылка хранится в личном результате, не отправляется в каталог команды, не
попадает в логи и исчезает из ответа при продолжении/ошибке/истечении срока.
При восстановлении после сбоя ожидающее задание завершается, новый браузер
повторно не запускается. Все сессии закрываются в finally.
При интерактивном доступе ограничения известных доменов дополнительно заданы
на всю сессию через Cloudflare guardrails, включая новые вкладки Live View.

До ручного ввода допускается небольшой JPEG-снимок гостевой страницы (до
80 000 символов base64). Он виден владельцу в подробностях сбоя и заменяется
вместе с последним заданием. После начала ручного ввода новые снимки не
сохраняются: при последующей ошибке может остаться только первоначальное
гостевое изображение. Снимки ввода, пароли, cookies и записи сеанса не собираются.
Во время ожидания отправляется только служебный Browser.getVersion, чтобы
сессия не закрылась от простоя. При сбое процесса действует короткий keep_alive.

Документация: [Live View](https://developers.cloudflare.com/browser-run/features/live-view/),
[Human in the Loop](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/).

## Бесплатные лимиты

Проверено по документации 23 ноября 2026 года: Workers Free включает 10 минут
Browser Run в сутки и запуск нового браузера раз в 20 секунд. Исполнитель
резервирует до восьми минут на день UTC и не более восьми запусков, один одновременно.
Обычный запуск резервирует минуту; ручной этап требует ещё две минуты и
проверяет остаток до создания ссылки. Поэтому при ручных проверках число
доступных запусков может быть меньше восьми. Исполнитель
закрывает браузер в finally и останавливается при отказе платформы. Квота общая
с другими браузерными приложениями аккаунта. Платный тариф не включается кодом.

Источники: [лимиты](https://developers.cloudflare.com/browser-run/limits/),
[тарификация](https://developers.cloudflare.com/browser-run/pricing/).

## Подключение к существующему сайту

Это действия публикации; подготовка ветки сама их не выполняет. Сначала
проверяются текущий тариф Free и доступ Browser Run в аккаунте Cloudflare.
Не подменяйте текущую конфигурацию нейтрального прототипа: для Fashion Radar
предусмотрен отдельный приватный исполнитель.

1. Собрать приложение: `npm ci`, `npm run check`, `npm run cf:build`.
2. Проверить упаковку без публикации:
   `npx wrangler deploy --dry-run -c workers/cloud-browser/wrangler.fashion-radar.jsonc`.
3. После разрешения владельца опубликовать **сначала** исполнитель:
   `npx wrangler deploy -c workers/cloud-browser/wrangler.fashion-radar.jsonc`.
   Его имя `kadr-fashion-radar-executor`; workers.dev и preview URL отключены.
4. Опубликовать существующее приложение с привязкой к исполнителю:
   `npm run cf:deploy -- --config wrangler.fashion-radar.jsonc --keep-vars`.
   Существующие переменные Supabase должны сохраниться. При Git-деплое эту же
   конфигурацию нужно использовать в команде публикации.
5. Войти в «Кадр» участником/администратором, открыть «Сбор роликов» и выполнить
   один запрос на 5 роликов с периодом «Все доступные даты». Проверить исходные
   ссылки и фактически полученные показатели. Затем проверить период 24 часа.
   Отказ доступа нужно зафиксировать, а не выдавать за отсутствие роликов.

### Публикация через GitHub в панели Cloudflare

В Workers Builds это два отдельных приложения, подключённых к одному
репозиторию и ветке `fix/fashion-radar-cloud-collection`. Корневая папка обоих
приложений — `/`. Зависимости устанавливает Cloudflare перед командами.

Сначала приложение **kadr-fashion-radar-executor**:
- Build command: пустое поле.
- Deploy command:
  `npx wrangler deploy --config workers/cloud-browser/wrangler.fashion-radar.jsonc`.

После успешной публикации исполнителя — существующее приложение
**video-research-platform**:
- Build command: `npm run cf:build`.
- Deploy command:
  `npm run cf:deploy -- --config wrangler.fashion-radar.jsonc --keep-vars`.
- Убедиться, что доступные сборке переменные Supabase заданы и соответствуют
  текущему сайту; секреты не публиковать в GitHub и логах.

Не запускайте обе публикации как команды одного Worker Build: Cloudflare
выбирает целевой Worker через контекст сборки. Сначала сохраняются настройки
приложения, затем запускается новая сборка нужной ветки. Старая сборка из main
не подтверждает публикацию подготовленных файлов.

Для отката привязки используется прежняя команда публикации с wrangler.jsonc.
Сохранённые карточки и действующая схема базы этим не удаляются.

## Проверки и границы подтверждения

`npm run check`, `npm run cf:build`, `npm run test:e2e`.
Для установленного Chromium:
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e`.

Модульные тесты проверяют извлечение по структуре присланного кода, нули/NULL,
свежесть, фотографии, позднее появление выдачи, обработку ответов страницы,
ограничения и отличия ошибок от пустого результата. Изолированный UI-тест
проверяет опрос задания и сохранение его метаданных в настоящем временном
Supabase. Данные соцсети в тесте записанные, не живые. Отдельный тест нейтрального
источника проверяет сам запуск Chromium через локальный Wrangler Browser Run.

Успешные автоматические проверки не подтверждают доступность Instagram или
TikTok из аккаунта пользователя в Cloudflare. Живая проверка, публикация и
подключение существующего сайта требуют доступа к этому аккаунту. В подготовке
ветки нет публикации, изменения production Supabase или покупок.
